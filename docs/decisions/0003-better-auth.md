# ADR 0003: Better Auth for authentication, arriving in Phase 1

- **Status:** Accepted (Phase 0, 2026-10-08); implementation in Phase 1

## Context

TRASK needs email and password sign-in, database sessions, email verification, password reset and
optional TOTP, at no cost and without sending user data to a third party.

## Decision

- **Better Auth**, self-hosted inside the app, with database sessions in Postgres. It will live only in
  `src/server/auth` behind the `AuthPort` interface (`src/server/ports/auth.ts`), which `createAction`
  already depends on.
- **Phase 0 creates only the `User` table** with Better Auth's core user fields. `Session`, `Account` and
  `Verification` arrive in Phase 1 as an additive migration generated by the Better Auth CLI.
- **The proxy checks only that a session cookie is present** (`better-auth.session_token`, or its
  `__Secure-` variant). It decides early redirects to `/sign-in`; it is not authentication. The session is
  validated against the database where data is read (`AuthPort.getSession()`), including the
  verified-email check.

## Rejected alternatives

- **Auth.js:** credentials sign-in is discouraged there and database sessions with passwords take more
  custom code.
- **Hosted identity (Clerk, Auth0, Neon Auth):** user data with a third party, free tiers that can change,
  and a paid-by-default dependency, against the zero-cost rule.
- **Hand-written sessions and password hashing:** custom crypto and session handling is where subtle
  security bugs live.

## Consequences

- Until Phase 1, every non-public path redirects to `/sign-in`, which itself is not built yet (404).
- Anyone can set a cookie with the right name and pass the proxy. That only reaches pages that must
  validate the session themselves; an unauthenticated `/api/*` call gets a redirect, not a 401.
- The `User` table has no row-level security and `trask_app` has full DML on it. Phase 1 decides how
  user rows are protected (RLS or an auth-only client), together with the auth tables.
- Email addresses are not lowercased by the database yet; Phase 1 handles it with Better Auth.
