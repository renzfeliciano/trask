# ADR 0004: Tenant isolation with composite foreign keys and row-level security

- **Status:** Accepted (Phase 0, 2026-10-08)

## Context

Every board, task and comment belongs to one workspace. A missing `where workspaceId` in one query, or a
child row linked to another workspace's parent, would leak data across tenants. Application checks alone
fail the day someone forgets one.

## Decision

- **Composite foreign keys.** Every tenant table has `workspaceId` and `@@unique([id, workspaceId])`;
  children reference `(parentId, workspaceId)`. `Task → Column` goes further, `(columnId, boardId,
workspaceId)`, so a task's column is on the task's own board. All composite relations use
  `ON UPDATE RESTRICT`: a cascaded key update would move a whole subtree into another workspace, and
  referential actions bypass RLS. `Task → Column` is `ON DELETE NO ACTION`: deleting a column that still
  holds tasks must be an explicit decision.
- **Row-level security, `ENABLE`d, not `FORCE`d.** `trask_app` is not the table owner, so policies always
  apply to it. `FORCE` would also apply them to the owner and make the `SECURITY DEFINER` membership
  function recurse into its own policy. Every policy (USING and WITH CHECK) is
  `app.is_member("workspaceId") AND (app.current_workspace_id() IS NULL OR "workspaceId" = app.current_workspace_id())`
  (`id` instead of `"workspaceId"` on `Workspace`). `app.is_member` reads `WorkspaceMember` for
  `app.user_id`; `app.current_workspace_id()` reads `app.workspace_id`. Unset user context means no rows
  (fail closed).
- **Workspace-scoped access (Ruling R39).** `createAction` authorizes a role in ONE workspace, so the
  database must confine that request to the same workspace. Otherwise an OWNER of W1 who is a VIEWER of W2
  could send `{ workspaceId: W1, boardId: <a W2 board> }`: the role check passes in W1 and a
  membership-only policy accepts the write to W2.
- **`withWorkspace(ctx)`** (`src/db/tenant.ts`) runs every operation as a batch transaction:
  `set_config('app.user_id', …, true)` and `set_config('app.workspace_id', …, true)`, then the query. Both
  ids are validated as UUIDs and the workspace id is lowercased. **Repositories for workspace-owned data
  MUST use `withWorkspace` with the `WorkspaceCtx` that `createAction` passes to the handler.**
- **`withTenant(ctx)`** sets only `app.user_id` (the workspace setting is empty, so the scope check is
  off). It is for reads that span the user's workspaces (list my workspaces and memberships) and for
  `app.create_workspace()`, never for workspace-owned writes.
- Both settings are transaction-local, so they never survive on a pooled connection.
- **Workspaces are created only through `app.create_workspace()`**, which makes the current user OWNER.
- **Grants:** `Activity` is `SELECT, INSERT` (append-only); `AuditEvent` is `INSERT` only, outside RLS,
  and written with `createMany` (no `RETURNING`, which would need `SELECT`).
- **Idempotency lives on the entity:** a create that needs it adds a nullable `idempotencyKey` with
  `@@unique([workspaceId, idempotencyKey])`; no generic store.

## Rejected alternatives

- **Application filters only:** one forgotten filter is a breach.
- **`FORCE ROW LEVEL SECURITY`:** breaks the definer function (above) and gains nothing while the app
  role is not the owner.
- **Schema or database per tenant:** migrations multiply; Neon's free tier limits databases.
- **Session-level `SET app.user_id`:** leaks between requests on pooled connections.
- **Membership-only policies** (the first Phase 0 cut): a role granted in one workspace could be spent on
  another workspace's rows, as long as the user was a member there at any role.
- **Role checks in SQL policies:** duplicates `permissions.ts` in a second language, and every new
  permission would need a migration.

## Consequences

- **RLS separates workspaces, not roles.** Inside the workspace a request is scoped to, any member, even
  a VIEWER, can write owner-level changes at the database level: `createAction` + `assertCan` is the only
  role barrier. Under `withWorkspace`, RLS also refuses every row of the user's other workspaces, so a role
  checked in one workspace cannot reach another. Under `withTenant` it refuses only workspaces the user
  does not belong to.
- **The workspace scope holds only if repositories use `withWorkspace`.** A workspace-owned repository
  written with `withTenant` reopens the cross-workspace gap. Reviews check this; a lint rule can enforce it
  once domain repositories exist.
- **Ids must be generated by the server.** Unique checks run before RLS: a client-chosen id that collides
  with another tenant's row (e.g. `INSERT … ON CONFLICT`) reveals that it exists. Ids come from
  `uuid(7)` defaults; inputs never carry ids for new rows.
- **`AuditEvent` is not tamper-evident.** Any `trask_app` session can insert an event for any workspace;
  it cannot read, change or delete events. Hash chaining or an external sink comes later if needed.
- **The `User` table is outside RLS** (Phase 1 decides, ADR 0003).
- **One statement per transaction.** `TenantDb` hides `$transaction`; several statements that must
  commit together need a tenant-aware transaction helper first.
- **Prisma warns on every command** that `onDelete: SetNull` is set on a relation with a required field.
  `Task.parentTask` uses `(parentTaskId, workspaceId)`; the migration is hand-edited to
  `ON DELETE SET NULL ("parentTaskId")` (Postgres 15+), so only `parentTaskId` is cleared. The warning is
  accepted.
- `Activity` and `AuditEvent` entity ids have no foreign keys: history outlives the entities.
- Moving a board to another workspace needs explicit copy logic (keys cannot be updated).
